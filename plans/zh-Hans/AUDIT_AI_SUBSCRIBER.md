### 问题1：`bonus_200` 边界值缺失 —— **严重性：中**

**问题描述：** 当现金恰好等于 $500 时，代码行为与需求不符。

- **需求**：`$300~$500` 区间得 **50**，`>$500` 得 **10**
- **代码**：`else if cash < 500 { 50 } else { 10 }`
- **cash=500 时**：`cash < 500` 为 `false`，走 `else` 分支返回 **10**
- **需求期望**：cash=500 属于 `$300~$500` 区间，应返回 **50**

**修复建议：** 将 `cash < 500` 改为 `cash <= 500`。

```rust
// 当前代码（有误）：
"bonus_200" => {
    if cash < 300 { 70 }
    else if cash < 500 { 50 }   // cash=500 时不进入此分支
    else { 10 }                  // cash=500 时错误地返回 10
}

// 修复后：
"bonus_200" => {
    if cash < 300 { 70 }
    else if cash <= 500 { 50 }  // cash=500 时正确返回 50
    else { 10 }
}
```

### 问题2：`get_out_of_jail` 的"现金紧张"分支永远不可达 —— **严重性：低**

**问题描述：** 评分前的过滤逻辑（第93行 `if cash >= *price`）确保进入 `card_score()` 时 `cash` 已经 ≥150，导致 `cash < 150` 的分支永远不会被执行。

```rust
// 第90-99行：过滤逻辑
for (card_id, price) in CARDS {
    if cash >= *price {                  // ← 进入前 cash 已 ≥ 150
        let score = card_score(...);     // ← 内部 cash >= 150 永远 true
    }
}
```

**影响分析：** 不影响功能正确性，因为买不起的卡片不会进入评分系统。但需求文档中的"现金紧张→30"分支在代码中实际上是无用的死代码，属于需求描述与实现之间的冗余。

## 3. `handle_sent_to_jail()` — 监狱分阶段策略审计

### 需求对照

| 阶段 | 需求条件 | 需求行为 | 代码条件 | 代码行为 | 结果 |
|------|---------|---------|---------|---------|------|
| 有免罪卡+后期 | ≥3地产 + 有卡 | 使用卡片 | `has_card && owned >= 3` | 使用卡片 | ✅ |
| 前期 | ≤2地产 **或** 现金>$1500 | 支付保释金 | `owned <= 2 \|\| cash > 1500` | 支付 | ✅ |
| 后期 | ≥3地产 | 留在监狱 | (上述条件都不满足) | 留在监狱 | ✅ |
| 无法负担 | 现金 < 保释金 | 留在监狱 | `cash < bail` | 留在监狱 | ✅ |
| 保释金计算 | jail_turns × $50 | — | `jail_turns * 50` | — | ✅ |

### 问题3：需求文档中"前期"条件与"后期"条件有逻辑重叠 —— **严重性：低**

**问题描述：** 需求表格中"前期"的条件为"≤2地产 **或** 现金>$1500"，"后期"的条件为"≥3地产"。当一个玩家拥有≥3个地产且现金>$1500时，两项条件都满足。

**具体场景：** owned_count=3, cash=2000
- 根据"前期"条件（现金>$1500）：应支付保释金
- 根据"后期"条件（≥3地产）：应留在监狱
- 需求本身存在条件重叠，未定义优先级

**代码处理：** 代码按照需求表格的文字实现了 `||` 关系，所以当 cash>1500 时（无论地产数量），都会支付保释金。这严格执行了需求文档的字面描述，但"后期+现金多"的场景策略可能需要业务决策者确认。

> ℹ️ **建议：** 如果"后期留在监狱"的策略优先级更高，应将条件改为互斥的 `if-else if`，将"后期"检查放在"前期"之前。当前实现是严格按照需求文档字面写的，不是代码 bug，但值得指出设计层面的歧义。

### 问题4：代码执行顺序与需求表格顺序不同 —— **严重性：轻微**

**需求表格顺序：** 有免罪卡+后期 → 前期 → 后期 → 无法负担
**代码顺序：** 有免罪卡+后期（第174行）→ 无法负担检查（第191行）→ 前期（第197行）→ [否则]留在监狱

代码将"无法负担"检查提前到了"前期/后期"判断之前，这实际上更安全——先确保能付得起保释金，再做策略决定。不影响正确性，符合防御式编程风格。
